ACRYL CLI Surface — How It Works

pnpm acryl → one process · one cordis root · one durable log

Typing pnpm acryl starts one Node process that owns one local Cordis runtime. The terminal is styled by acryl-cli; the runtime itself is assembled and booted by acryl-harness-runtime — the only package that knows how to compose the pinned DeepSeek Harness (@deepseek-ai/dsh-*) into a live profile. The TUI is a direct host: no server, no loopback — just a durable session log on disk and a single in-process seam between surface and runtime.

Launch Chain

Eight hops from the shell to a mounted terminal. acryl-cli/bin/dev-run.mjs rebuilds acryl-cli/lib only when a source mtime is newer than the build output. bin.ts re-execs Node with --expose-internals because the profile mounts Cordis HMR. runAcryl() rejects acryl web / acryl gui and non-TTY stdin/stdout; --json is a headless boot-probe that prints status and disposes.

Why a relaunch? The composed patches always contain the hmr row (@deepseek-ai/cordis-plugin-hmr), and bootAcrylHarnessProfile() hard-fails without --expose-internals. node-launcher.ts re-spawns the same script with that flag, forwards the exit code, and the child proceeds — so the process you talk to is always the relaunched one.

Package Topology

The dependency rule: surfaces → harness-runtime → pinned harness, with acryl-control supplying shared types. Nothing depends on a surface, which is what makes the runtime swappable across terminal, web, and desktop.

Runtime Boot — bootAcrylHarnessProfile()

acryl-harness-runtime/src/index.ts turns a profile name into a live Cordis root Context. The Cordis root config itself is empty ([]) — everything is ordered patch entries applied by the Loader, activation being service-availability driven (row order carries no load semantics; a later id-targeted row replaces a row's whole config, it never merges).

01
resolveProfileDir('acryl')$DSH_HOME → ~/.dsh/profiles/acryl
TUI uses the shared DSH home (DSH_HOME env can override; desktop uses its own ~/.dsh-acryl). Names validated, no path tricks allowed.
02
initProfile()manifest + cordis.patch.yml + pnpm-workspace.yaml
Idempotent seeding — never overwrites. Manifest declares bundles: ["@deepseek-ai/dsh-base"]; user patch layer starts as [].
03
healProfilesModuleFallback()profiles/node_modules symlinks
Ensures the installation fallback resolves bundle packages for the profile loader; repairs wrong links, throws on real directories.
04
loadProfile('acryl', …)bundles → layers → patches
Loads dsh-base's include tree + its giant insert patch, plus the user's patch layer.
05
compose patch pipelinedsh-base layers → ACRYL capability rows → user layer
structuredClone'd, ordered. ACRYL rows override system-prompt and insert agent-presets, session-stats, authorization. User layer wins last per row.
06
HMR guardrequires --expose-internals
Finds the hmr entry in the composed patches; throws before boot if the process wasn't relaunched exposed. The CLI's relaunch (Fig. 2) always satisfies it.
07
await boot('acryl', …)Loader install → patch apply → activation
Activates every row when its dependencies exist; runs the optional prepare host hook (the web variant uses it to provide cmdline).
08
installAcrylWorkspaceStatusTool(ctx)ACRYL's model-facing tool
Ordinary Cordis plugin: injects tools, registers acryl_workspace_status via defineTool, typed output schema + separate render, honors exec.signal, disposes with its Fiber.
09
return frozen runtime handle{ ctx, profileDirectory, dispose() }
startDirectHost checks readiness (ctx.get('sessions') + ctx.get('agents')); dispose awaits ctx.fiber.dispose() — every plugin disposer, in dependency order.

Service Composition

What ends up resolvable on ctx. Layer 1 is dsh-base's one giant insert (grouped below by domain); Layer 2 is ACRYL's capability patch; Layer 3 is the user's cordis.patch.yml (empty here, wins last).

LLM plane

  • llm registry · llm-retry
  • llm-deepseek native adapter — key resolves per request
  • llm-pi-ai multi-provider twin, mounted dormant — zero routes until a llm-pi-ai: settings section names providers (what /login drives)
  • settings ($DSH_HOME/settings.yaml, hot-reload) · credentials (env → .credentials.yaml → .env)

Session plane

  • session durable event log
  • session-persistence-jsonl → ~/.dsh/sessions (what --resume reads)
  • titles (LLM), user-questions, attachment-local (content-addressed images)
  • session-query-sqlite openAt: never — search off, exact reads fine
  • checkpoint policy · projection · telemetry-otel DISABLED by default

Agent plane

  • agent service (ctx.agents)
  • agent-loop with no startup agents — sessions created on demand
  • agent-default-model: deepseek-official / deepseek-v4-flash
  • agent-instructions (AGENTS.md, 64 KiB cap)

Isolation & approval

  • sandbox-local + policy workspace-write (DSH_PERMISSION_MODE)
  • approval = ask (never under danger-full-access)
  • permission presets: read-only · workspace-write · danger-full-access
  • fs-sandbox cwd = process.cwd() · bash/pwsh sandbox per platform

Tool registry

  • tools registry + bash/pwsh, fs, fs-search, str-replace-editor (16k cap)
  • skill · todo · goal · web (fetch: false, search-only)
  • subagent (spawn, continuable) · subagent_fork (one-shot) · control · workflow · ralph
  • timeout policy · repeat-reminder (3/5/8) · spill 50k · tool-result-pruner

Commands · goal · plan · context

  • commands registry + feedback
  • goal + round-driver + /goal
  • plan-mode section: explore first, no mutations, exit_plan_mode presents
  • token-meter · compaction-basic · /compact

Session Bridge — Data Flow

The TUI touches the runtime only through createAcrylSessionBridge() (types from acryl-control). Two channels feed the UI: raw SessionEvents for the transcript, and periodic AcrylSessionSnapshots for status. Both fold from the durable log — the log is the source of truth, the store is a cache.

Surface Parity

Same runtime vocabulary, three presentations. The CLI is the only direct host; web and desktop serve the same composition over loopback transports.

TUI vs Web vs Desktop
AspectTUI · pnpm acrylWeb · acryl-webDesktop · acryl-desktop
Process modeldirect host one process owns the Cordis root, no serverruntime serves HTTP/WS on loopback; sandboxed renderer, no Electron APIsElectron main boots Host via Cordis; renderer served over loopback
Session accessin-process bridge, attachment: 'owner'protocol client over transportHost/client faces
UI toolkit@earendil-works/pi-tuidsh-web-app bundledesktop shell + Development Canvas
Capability patchespersona + presets + stats + authorizationauthorization onlydesktop profile composes its own rows
DSH home~/.dsh (shared)~/.dsh~/.dsh-acryl (isolated)
Continuityacryl tui --resume <id> · same $DSH_HOME/sessions JSONL · same snapshot types from acryl-control
Direct-host trade-off. In-process hosting means no bootstrap race and immediate cancellation/snapshots — but a direct host cannot share its live runtime with a second surface. Attaching another viewer to a running session is the web/desktop protocol layer's job, not the TUI's. Continuity is external either way: the process is disposable, the durable log survives.
