# Persistence, registries and starters: everything is a git repository

Status: accepted direction (2026-09-27, owner), built in the order at the end. Product definition: `framework.md`. Repository organization: `repositories.md`.

## The need

The public registry offers `acryl.blank` and pre-built starter Blueprints (an accounting starter, a sound-stage starter), from which users develop unique,
often proprietary products. Some users publish starters openly; many never will: it is their work, and it goes to their own private repository. And many users are
new to software (product people with a vision, not developers): they need saving, versioning, CI and releases handled from inside the app.

## The model: three kinds of git repository, one transport

ACRYL builds no hosting, accounts or registry server. Every storage place is a git repository with a known layout, reached with the user's own git credentials.

| Kind | Repository | Visibility | Command |
| --- | --- | --- | --- |
| **An app** (persistence of one product) | the app folder (`acryl new` makes it a repository) | private by default, on the user's own host | `acryl remote connect` once, then `acryl save` (in the app: `/app save`) |
| **A registry** (catalog of Blueprints and Blends) | `blends/<id>/` folders plus a CI-built `index.json` | public: acrylblends.github.io, moderated by reviewed pull requests; private: a company's own repository in the same layout | `acryl publish --to <registry>` opens a pull request, never pushes directly |
| **A starting point** | any of the above | whoever has access | `acryl new <dir> --from <registry id \| git URL \| folder>` |

A private starter therefore needs no registry: `acryl new my-app --from git@github.com:agency/accounting-blueprint.git`. A private registry is the public registry's
layout on a private host. The registries a user reads from are their own settings (user config), not an app's.

## Lifecycle from inside the app

1. First save: the app asks where to keep the project (private or public, which account) and creates the repository through the user's own `gh` login; ACRYL
   stores no token. Private is the default.
2. Saving afterwards is one action; the agent may propose it after a working change, with a clear message.
3. CI from day one: `acryl new` writes a workflow that validates `blend.yaml` and runs the app's checks on every push. Releases (`acryl package` on a tag, attached
   to a release) follow once packaging exists.
4. Publishing a starter to a registry is a separate, explicit act.

## Guards (the risks this design must not create)

- **Leaking proprietary work.** `blend.yaml` records `visibility` (`private` | `public`) and `license`. A push of a private app to a public remote, and a publish of a
  private app, are refused. Connecting a remote and every publish need a human confirmation; the agent can propose them, never perform them alone. Routine saves
  to the app's own private remote may be allowed after the user opts in once.
- **Secrets in git.** Runtime data (`.dsh/`) is ignored from the first commit. Every save runs a secret check on what is about to be committed and refuses on a hit.
- **No stored credentials.** Git and `gh` use the user's own credential helpers; ACRYL never reads or writes tokens.
- **Moderation.** The public registry accepts starters by reviewed pull request; the index is built by CI only from entries that validate with `@acryl/blends-core`.

## Registry layout

```text
registry/
  index.json                 generated by CI: one entry per starter (id, name, kind, version, category, description, license, path)
  blends/<id>/blend.yaml     the starter's definition (a Blueprint, or a Blend with lineage)
  blends/<id>/blend.lock.json, extensions/, README.md, screenshot.png (optional)
```

Registry ids are the manifest ids (`acryl.blank`, `acme.accounting`). Categories follow `docs/acrylbelnds_100ctgs/`.

## Build order

1. Registry format and index generator in `@acryl/blends-core`; `acryl new --from <git URL | registry id | folder>` with git as the transport. Local only.
2. App persistence: `visibility` and `license` in the app definition, `acryl remote connect`, `acryl save` with the secret check and the visibility guard, the CI
   workflow in `acryl new`.
3. The public registry on acrylblends.github.io (blank and the first starters, CI building `index.json`, a catalog page), and `acryl publish`.
4. Archive `acryldev/blends`.
