Spec 056 - UX/UI study

lvbluxui: a chat-first app builder, screen by screen

Redrawn from 34 screenshots of one product, in neutral styling. No logos, no copied artwork, no real names. One of the four studies in spec 056; the design tokens match the ACRYL AOS study so the four read as one set.

What the product is

It is a chat-first builder for web apps. You start on a dashboard with one prompt box and a visible mode switch (Build, Chat, Plan), and the product writes and runs a whole app against its own hosted backend. Inside a project the screen is a three-part workspace: a narrow rail with the workspace, New, Search, Projects, Connectors, Automations and recent apps; a chat column where every turn is a prompt plus a result object you can inspect (a title, Details and Preview toggles, a checklist of what changed, an undo); and a canvas with four tabs, Preview, Code, Files and More. The canvas bar carries the device toggle, a route picker, Share and Publish, so the two outward actions are always one click away. Everything that is not chat or preview lives under More as a second level of pages: analytics, cloud, AI usage, agent integrations, payments, connectors, security, SEO and settings. Sharing is per project (email invite, invite link, workspace access). Publishing is a one-way live URL on a subdomain, with a security line checked before the button. Versions and a version history do not appear in any of the screens: the only trace is an "AI edits count" row in a settings page.

Solid arrows are visible in the screens. Dotted arrows are the parts of the usual flow (versions, GitHub) that the screens do not show.

Version history is the notable gap. A builder that publishes has to answer "what is live, and how do I go back"; this product answers the first half in the Publish panel and leaves the second half to an "AI edits count" row and an Undo on each result card. GitHub appears once, as a Settings row, and the page behind it is not in the screens.

Take for ACRYL, do not take, and why

Take for ACRYLDo not takeWhy
Home is one prompt box with a visible mode switch (Build, Chat, Plan), each mode with a one-line consequence.The credit counter and the Upgrade button inside the chat column.The mode switch decides what the agent will do, which is the one thing a person needs before typing. The credit banner decides only whether they may continue, and it interrupts every build.
One project shell: rail, chat, canvas, with Preview, Code, Files and More as tabs of the canvas.Read-only code and file views, with a "Read only" badge and Download as the only action.The shell is the right shape for ACRYL's frame. But ACRYL's people edit code, so Code and Files must be equal surfaces, not viewers with a download link.
Each agent turn is an object: a title, Details and Preview toggles, a checklist of what changed, an edit count and Undo.-Spec 055's History needs one inspectable object per change. A checklist plus Undo gives a person the same facts in the chat that History will show in the panel.
Publish panel: one state line, the live URL row with rename, who can open it, a security line, then the button.Turning the domain row into a Pro upsell next to the URL.Spec 055's Publish needs exactly these facts in one place. The upsell sits on the one row a person must read, which makes the important panel look like a shop.
Device toggle, route picker and open-in-new-window on the canvas bar.-Preview and share are per page, so the page picker belongs next to the preview. A route list read from the app also means a shared link can point at a page that exists.
Annotation tools on the preview: select an area, add text, draw, comment, with the target sent as the next chat message.Hiding theme, dock and shortcuts in an overflow "..." beside the tools.Pointing at a region is the cheapest precise change request, and an agent can take the region as a structured target. The four tools deserve one visible row; the placement and theme switches can live in the overflow.
Connector catalog grouped by outcome (Grow, Sell, Communicate, Work, AI), with Add custom, MCP server and MCP registry as three explicit doors.A second top-level Connectors product with its own sidebar, its own search and an "Enabled 7" counter.Outcome grouping matches how a person asks for help, and ACRYL's plugin model is already MCP-shaped. But a parallel navigation beside the app list duplicates the frame, and the counter answers a question nobody asked.
One More area per app holding analytics, AI usage, security, SEO, domains and settings, each with an empty state that names the next action.-ACRYL's Settings today is app-level. Per-app settings, usage and security need one door; a settings page per feature would scatter them again.
Security before publish: quick scan automatic on every publish, deep scan on demand, dependency count with known issues.-It makes publish a reviewed step without adding a second workflow: the review happens in the same panel that ships the app.
Git as a project-level action, visible in the same bar as Publish and Share.Burying Git as the last row of a settings sidebar, with the page never shown.Spec 055 makes GitHub sync a first-class action. The screens put Git three levels down, which is where a feature goes to be forgotten.
-The push-notification opt-in card inside the project chat.It sits in the chat's most valuable place, the last block before the composer, and asks for a marketing permission in the middle of a build.
-A gradient hero and a template gallery as the home screen's main content.It pushes the person's own apps below the fold. ACRYL's home has apps, a store and a workshop to show, and the prompt box does not need a gradient to be found.
-The "Share this product, up to 400 credits per referral" card pinned to the rail bottom.Permanent marketing inside the product. ACRYL has no referral programme, and the slot is better used for the app's own state.
-Automations as a top-level rail item with a page that has no fields and no link from an app.In the screens it is one empty page with two identical buttons. ACRYL's scheduled runs belong to the app that uses them, not to a workspace-level page that cannot say what a task is.
